Drove the fixture app (served on http://localhost:7003, static server) with puppeteer-core + real Chrome and read the DOM, console and network after each step. Invalid email (name "Ada Lovelace", email "ada@clinic", password 15 chars): the form does NOT submit. Only the email field shows "Enter a valid work email" (red text under the field); name and password errors stay empty; no success message; zero network requests. All three fields empty gives three messages (name, email, "Use at least 8 characters"). Valid data (Ada Lovelace / ada@clinic.example / 15-char password / 4-10 therapists): all errors clear and a green status box appears: "Account created for ada@clinic.example. Check your inbox." Submitting causes zero network requests: the "account" is never sent anywhere, so the app only claims success client-side. Fixing a previously invalid email and resubmitting also clears the old error text correctly. Other findings, all observed: - HTML injection: the success message is built with innerHTML using the raw email. The email regex accepts markup (no spaces), e.g. <img/src/onerror=window.__xss=1>@a.co passes validation and the injected img's onerror fires (window.__xss === 1). Self-inflicted here (you only inject yourself), but it becomes a real XSS the moment that string comes from a server or URL. Fix: textContent or escape. - Accessibility: the error divs are not linked to the inputs (no aria-describedby/aria-invalid; aria-invalid is null after a failed submit), they are not live regions, and focus stays on the submit button instead of moving to the first invalid field; screen reader users get no feedback. The success box does have role=status. - The regex rejects "ada@clinic" even though the HTML spec allows it (fine for a work-email form), and the form has novalidate so the browser's own validation never runs. Not testable here: real account creation, since the app has no backend (the only network request in the whole session was GET /favicon.ico -> 404).
